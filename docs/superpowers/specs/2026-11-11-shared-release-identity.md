# Shared release identity

Implement the approved design: a module/version identifies one immutable source commit and tracked build-input fingerprint, independent of destination. Reserve an annotated `release-identity/<module>/<version>` Git tag atomically with the first destination reservation. Its JSON record contains `schema: 1`, `module`, `version`, `source`, and `fingerprint`. Publication records embed that object as `release_identity`; per-destination tags, pending/upload markers, verification hashes and confirmation states remain independent.

Preparation considers shared module history across providers. A matching second destination reuses the exact canonical commit; changed build inputs require a newer version. Explicit reuse of an existing canonical version is allowed only for matching inputs. Matching retries resume safely; uncertain Central uploads go through confirmation/finalization and are never blindly uploaded again. Create-only atomic leases prevent competing destinations from reserving different sources for one version. Identity checks also guard confirmation, finalization and override paths.

Legacy provider-specific releases remain immutable and recoverable, including existing conflicts. Do not invent a canonical identity for historical divergent releases or reuse their version for a new reservation. New versions start above existing module history. Documentation archives combine destinations only when a shared identity proves equality; historical routes and source provenance remain valid. Provider-specific artifact bytes can differ due to metadata/signing. Build-input equality is tracked configuration/source equality, not a claim of bit-for-bit reproducibility.

Keep the external prepare outputs compatible. Shared identity/configuration is checked before building and again before reservation. The workflow's baked build settings must match the selected canonical source, or preparation rejects reuse. Retain Rust-only operation and credential-free regression tests using local Git remotes and fake registries. No real publication or release-tag mutation is part of implementation validation.
